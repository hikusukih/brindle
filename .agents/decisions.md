# Process decisions

How agents are managed here: sessions, the plan, scheduling. Product decisions are in `docs/decisions.md`. Same rules as there: open questions first with a recommendation, settled decisions below with the reason.

## Open

- **Migration numbers collide between open box PRs.** Drizzle numbers migrations in order (`0003_...`), so two box PRs that change the schema in parallel each pick the next number and the second to merge conflicts in `drizzle/meta/_journal.json`, in the snapshot of that number and in `src/server/db/schema.ts`. It happened in the run that filed this: P4.2 (#62) wrote 0003 and had to be renumbered to 0006 after P2.4 and others took 0003 to 0005, and P4.4 (#88) wrote 0005 and went to 0006 the same afternoon, so whichever of those merges next will collide again. The fix each time was the same: keep both sides of `schema.ts`, delete the branch's own migration SQL, take `main`'s journal and snapshots, and run `npx drizzle-kit generate` again. Recommend writing exactly that into `CLAUDE.md`'s steps for merging `main` into a box branch (the user's edit, since sessions may not change `CLAUDE.md`), so an unattended session does not have to rediscover it, and adding nothing else: a lock or a reserved-number scheme would add process for a conflict that takes a minute to resolve and that only the second merger sees.

## Settled

- The user's attention is the scarce resource, so it goes through one place. On 2026-11-06, 70 PRs were open, 54 of them `[plan]` PRs, none merged in five days, while box PRs merged at about 2.5 a day; a box PR reviewed ready on Oct 31 (P2.11) went stale waiting only because it split its box. So: a daily-rebuilt status page lists what waits on the user with one-tap answers, which a scheduled session acts on and records in the repo; questions are asked once, on the page, never as `Ask:` PRs; at most 10 open `[plan]` PRs; and bookkeeping plan changes (when or how a box is tracked, never what is built) merge like code boxes. Rejected: one batched proposal PR a week, since one idea per PR still lets the user take or leave each, and the page gives the overview a batch was meant to; letting agents merge any plan rewording, since rewording a box can drop scope as surely as deleting it. Chosen by the user on 2026-11-06.
- Sessions trust only the repository owner's account. The repo is public, and the rules told the user apart from sessions only by the Claude Code footer, so any stranger's comment counted as the user's, and a fork PR named like a box or titled like a bookkeeping `[plan]` PR could be merged by a session after a clean review and 4 quiet hours. Now a comment is the user's only when the owner's account wrote it without the footer, and a `Brindle review:` counts only when the owner's account wrote it with the footer, so a stranger can't fake one; outside PRs are never merged, fixed or answered by a session on its own and go to the status page; and the review task reads an outside PR but never runs its code, since that would run a stranger's code in a session holding the user's GitHub access. Chosen by the user on 2026-11-06.

- Work happens in Claude Code on the web sessions, which push a branch and open a PR. Sessions never merge their own PRs. A later session may merge a box PR of code or UI work once it has no conflict, green checks, no open questions and 3 quiet hours (`CLAUDE.md`, Merging box PRs), so the queue doesn't stall on the user for work CI can judge. The user still merges design notes, review boxes, `[plan]` proposals, decision PRs and anything labeled `needs-careful-review`, because those are where the user reviews ideas. Later sessions also fix the findings of a `needs changes` review on ready box PRs, since the session that built the box has ended and the user would otherwise be the only one to act on it. Merging right away by the session that did the work was rejected: no one but CI would see the code before `main`, and the user would have no window to stop it.
- The plan lives in this repo (`.agents/plan/`), not anywhere else. It is one file per box in a folder per phase, with no index, and checking a box moves its file into the phase's `done/` folder. It was one `PLAN.md`, and 35 of 115 merges replayed in November 2026 conflicted there, mostly a proposal inserting or rewording a box beside one a box branch was checking. Separate files keep those changes apart. The cost is that the queue's order comes from IDs (lowest phase, then lowest number) rather than position, so a box that must wait says so in its needs.
- The plan changes through `[plan]` proposal PRs kept apart from box work, so an idea that turns up mid-box is recorded and offered, not acted on or lost when the session ends. Each phase ends with a review box.
- Scheduled sessions work the queue unattended, started only by the clock. Five tasks run, each with its prompt in `.agents/ops/` and its times in `.agents/ops/schedule.md`: the box session (7 AM and 3 PM, boxes for up to 4 hours), the answers session (half an hour before each box session, acting on the user's answers on the status page), the status session (once a day in the evening: rebuilds the status page, then files proposals within the cap), the usage maximizer (Wednesday evening) and the PR review task (on PRs opened, plus 11:30 AM and 7:30 PM). Times are America/New_York, recorded in the repo by the user's choice. Boxes have stable IDs and explicit needs, and a pushed `box/<ID>` branch is the claim, so sessions never take the same box. GitHub Issues were rejected: the plan would live in two places, and plan changes would stop showing up as PR diffs.
- Two cycles a day, and answers get their own task. The user's weekly usage was going unspent, and they answer the status page a few times a day, but one daily run, after the box session, acted on the answers, so an approval tapped at noon freed a box only for the morning after next. So each day runs two cycles of answers (6:30 AM, 2:30 PM), then box (7 AM, 3 PM), then review (11:30 AM, 7:30 PM), and a status rebuild follows the afternoon box session (7:15 PM, before the 7:30 PM review, which mostly covers box PRs the user doesn't act on), since the user reads and answers most in the evening. The answers session is the only one acting on answers, so two runs can't merge or comment twice; the old weekly task, renamed Brindle Status, only rebuilds the page and files proposals, and the page is the status page, no longer called weekly. Each run is a fresh session, which keeps context windows small. Wait periods shrank to fit an 8-hour cycle: a cut-off box or `addressing-review` takeover after 4 hours instead of 6 (with an hourly push while working, so a quiet branch means the session is gone), and 3 quiet hours before a merge instead of 4, so a morning PR reviewed at 11:30 merges at 3 PM. "Later" now hides an item until the next rebuild instead of until 6 AM. The user accepted being the bottleneck: more output means more for them to read, which they prefer to leaving usage unspent. Rejected: running the whole old weekly task more often, which rebuilds and files proposals each time; having the box session apply answers itself, since one job per session keeps each context small. Requested changes are marked with the repo's existing `help wanted` label rather than a new `changes-requested` one, by the user's choice. Chosen by the user on 2026-11-08 and 2026-11-09.
- The slots design (`.agents/design/slots.md`: two box workers an hour and two planner runs a day) was settled but never installed, and its three prompts went stale, so it was retired in November 2026 and the prompts deleted. A settled decision nobody follows misleads every session that reads it. The four tasks above are what runs; slots stays as a record of the idea if more parallel workers are wanted later.
