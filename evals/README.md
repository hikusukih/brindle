# Evals

Scenarios in `scenarios/*.json` replay conversations against the harness: a channel, a list of user messages, a script for the scripted model, and per-run expectations (final status, stop reason, text the reply must contain, and in scripted mode the exact event types). A scenario may also declare fake `tools` (a name, an effect level and a fixed result) and answer approval cards with `approvals`; see `external-tool-waits-for-approval.json`. An expectation's `executed` lists the fake tools that really ran, so a scenario can assert that nothing external was sent; the `injected-page-*` scenarios use it to check that text from a fetched page can't skip the approval card (live, the model may or may not take the bait, and either way `executed` must hold). A scenario may also declare `mcpServers`: plug-in servers with fixed tools, registered through the same wrapper and effect rule as a real MCP server, so a tool's description or result can carry planted text and a tool with no assigned effect level can be checked to ask for approval (the `mcp-*` and `unclassified-mcp-*` scenarios). To add one, drop a JSON file in `scenarios/`; its shape is the `Scenario` type in `runner.ts`.

CI runs every scenario against the scripted model as part of `npm test` (`evals.test.ts`), so the plumbing is checked on every PR.

To run them by hand: `npm run evals`, optionally with a name filter (`npm run evals -- step-limit`).

To run them against a real model, which costs money and is worth doing when a harness change could move the results: configure it the way the server does (`BRINDLE_MODEL=openai:<model>` with `OPENAI_API_KEY`, or the Anthropic equivalents; see the README), then `npm run evals -- --live`. The script is ignored in live mode, so write expectations that any reasonable reply satisfies.
