# Decisions

Open questions first, each with a recommendation. A session that hits a question not listed here adds it with a recommendation and moves on to work that doesn't depend on it. Settled decisions move to the bottom with the reason, one line each.

## Open

- **Text-to-speech provider.** Recommend an OpenAI-compatible speech endpoint, so a local TTS server and a hosted one are interchangeable.
- **Web search provider.** Recommend a self-hosted SearXNG-style JSON endpoint named by an environment variable, with `web_search` registered only when it is set, because it needs no key and nothing about the user's queries goes to a third party by default. A hosted API (Brave, Tavily and the like) can be added later as a second backend behind the same tool if SearXNG proves unreliable. Box P2.3 lands this as `BRINDLE_SEARCH_URL`; closing this question confirms it.

- **Backup and restore.** Everything a user would grieve to lose (channels, goal state documents, artifacts, the vault) lives in one data directory on one host. Recommend documenting, not building, a first answer: a README section saying to stop the server or use SQLite's online backup for the database and copy the artifacts directory alongside it, and, once the vault exists, to back up its key file separately from the data directory so that a stolen backup does not open the vault. A built-in export can follow if the manual steps prove error-prone.
- **ACP delegates.** Whether a run may hand a task to an external agent over ACP (boxes P9.2 and P9.3). Recommend deferring it: the user sees no current need, has no agent in mind to verify against, and does not want to trust third-party agents with their files. Nothing built depends on it. A draft design note, with the protocol checked against the v1 schema, is parked at `docs/design/acp.md` with the status deferred; it is not approved, and P9.3 stays blocked. Settling this as "deferred" leaves the boxes waiting; reopen it when there is a specific agent worth delegating to, and re-check the protocol then, since the note will be stale.
- **DNS rebinding in `web_fetch`.** `web_fetch` resolves a host and refuses it if any address is private, but the fetch then resolves the name again on its own. A host whose DNS answers a public address the first time and a private one such as `169.254.169.254` the second (a rebinding attack) passes the check and is fetched. The P2.3 review (#32) noted the gap as acceptable for now, and no box covers it. Recommend closing it: connect only to an address that was checked, through a fetch dispatcher whose lookup refuses private addresses at connect time (an `undici` `Agent` with a `connect.lookup`, one small dependency that Node's own fetch is built on), with a test whose resolver changes its answer between calls. The alternative is to accept the gap and say so in `docs/design/tools.md`: it needs a hostile page and a DNS server the attacker controls, and a self-hosted single-user server is a small target.

## Settled

- Name: the persistent catch-all channel is the Home channel (it was the landing channel), and the channel that owns a reference document is its owning channel (it was its home), so one word doesn't carry two meanings. Chosen by the user in UI feedback on October 29, 2026.
- The Home channel knows the instance: a directory of active channels and goals, read tools across it, no summary. Text from other channels can now reach a run that also reads untrusted input; that is accepted because external actions, secrets and writes to shared things are held by approval cards, the key manager and versioning, and context isolation was a second line, not the first. Other channels can load the same directory on demand. Chosen by the user on October 29, 2026.
- Public repo, MIT license.
- Stack: TypeScript throughout, React + Vite + Tailwind PWA, Hono on Node, SQLite through Drizzle, SSE, Vitest, Docker. The most standard choice, so any agent can pick it up cold.
- The harness is ours; models are pluggable behind an adapter. Whether external agents plug in as ACP delegates is reopened under Open.
- The agent may ask for logins. Credentials go through the key manager, which is held to a higher bar than the rest of the code.
- Name: Brindle. Several AI-agent tools already use Bridle, and Bindle is a WebAssembly package system; no software named Brindle turned up. The rename landed as box P0.5.
- Where it runs: the Docker image on an always-on host, reached over a private network or a reverse proxy the operator already runs. Nothing in the code assumes a particular host.
- Default models: one strong model for conversation and goal planning, and one cheap or local model for watchers and summaries, chosen per **scope** in configuration. Models are reached through the OpenAI-style API first, since one adapter then covers local servers such as Ollama and hosted models alike (P2.2); the adapter contract (P1.3) is the interface that keeps other providers from becoming a big refactor.
- Card means only an item the user acts on (an approval, a suggestion, a credential request form). The purpose card was renamed purpose statement, and the shared type and table are `ScopeStatement`, `PurposeStatement` and `scope_statements`, so one word doesn't carry two meanings. Both terms are in the glossary.
- Master key for the vault: a key file outside the data directory with owner-only permissions, its path set by `BRINDLE_MASTER_KEY_FILE`, and an OS keychain as a later option. The vault starts without a key file and says so rather than generating one beside the data, so a backup never holds both. Settled with the key manager design note (P6.1).
- Calm is a design goal that guides the architecture and the defaults, not a limit on what the user wants: the harness starts quiet, and the user can turn up notifications, offers and chattiness. Chosen by the user in UI feedback on October 29, 2026.
- Run cost budget: deferred. Models run locally at first, so there is no price to track; a per-model rate table would only go stale. Runs are bounded by the step, token and time limits, and fitting a request into the model's context window is handled by context assembly (`docs/design/context.md`). Reopen when a hosted, paid model is in regular use.
- An RSS reader reads the Atom feeds with a separate feed token: a random value in the feed URL's path that opens only the Atom routes, read-only, shown on a settings page, revocable and replaceable at any time, and never accepted by the rest of the API. The login token never goes in a URL, and a leaked feed URL exposes only what the feed shows. P5.3 builds it. Chosen by the user on the status page on November 9, 2026, accepting the recommendation.
- The "an update is available" system report is dropped from `docs/architecture.md` until the project publishes versioned releases; there is nothing to compare against today, and a check would contact a third party from a self-hosted instance. When releases exist, the check is opt-in and off by default, once a day, comparing a version baked in at `docker build` against a releases URL the user sets. Chosen by the user on the status page on November 9, 2026, accepting the recommendation.
- The run token limit counts what the server had to read: uncached input plus output, using a cached-input count the adapter's usage report gains where the server gives one, and all input where it does not; each run's record keeps the number. A cached prompt re-sent at every tool step otherwise trips the limit after a few steps on a CPU-only host. Box P2.20 builds it. Chosen by the user on the status page on November 9, 2026, accepting the recommendation.
- Limits on schedules a model proposes (`propose_schedule`, P4.5): a schedule may fire no more often than every 15 minutes, and a goal may have at most 5 schedules. The user answered "15 minutes floor, 5 schedule cap"; the cap was 10 as built. Box P4.30 changes it. Chosen by the user on the status page on November 9, 2026.
- A waved-off "Start a channel for this?" comes back after a fixed cooldown: after Not now, no new-channel offer for the next twelve Home channel runs, then offers resume whatever the topic. The harness keeps the count, so rewording the suggested name can't get past it, and unlike the Home channel note's rule it can't hold the offer back forever. Chosen by the user on the status page on November 9, 2026, accepting the recommendation.
- The cap on scheduled runs stays one overall number by default, with an optional per-model limit on concurrent scheduled runs in the P2.11 model settings file, unset by default and checked alongside the overall cap, set from what the boundary suite (P2.10) reports against the user's servers rather than a guessed default. One number alone lets two slow runs on a large model hold both places while a small model's server sits idle. Box P2.24 builds it. Chosen by the user on the status page on November 8, 2026, accepting the recommendation.
- Wrong login tokens are slowed down, never locked out: a wrong token gets its answer after a delay that grows with the number of wrong tokens in the last few minutes (up to a few seconds), the right token is never delayed or refused, the 20th wrong token in an hour writes one system report, and a token chosen with `BRINDLE_TOKEN` must be at least 24 characters. No per-address limit, since behind a proxy every client shares one address. Box P5.12 builds it. Chosen by the user on the status page on November 9, 2026, accepting the recommendation.
- A linked channel's write to a goal's state document needs no card for now, even after the run read outside text, as the goal links note recommends: it relies on that note's limits (at most 3 writes per channel run, each shown in the channel with a Revert line and kept in the goal's history, and the next goal run told when the last writer was a channel run), since the state document can't widen any permission. The card is added if channel writes turn out to be reverted often. The write's Revert line (not a card, in the glossary's sense) must show where the user is at the moment the write is made, whichever channel or goal that is, not only in the transcript of the channel or goal whose state changed. The user answered: "Take the recommendation, as long as the card is displayed. It was unclear whether the card displayed only in the channel/goal whose statement was modified, or in the channel/goal where the change was proposed. The card should appear at the time the change is made, wherever the user is". Chosen by the user on the status page on November 9, 2026.
- "Another run handing off" is removed from the trigger lists in `docs/architecture.md` until a design note defines it; nothing defines or builds it, and P4.12's `runs.trigger` has only `user` and `schedule`. Accepted suggestions stay, since P7.2 builds them. Chosen by the user on the status page on November 9, 2026, accepting the recommendation.
- Move offers stay in the Home channel only. An ordinary channel's run, given a message that doesn't fit its purpose, uses the directory (`load_system_context`) to answer and to name the channel that fits in its reply; it already has the drift nudge, whose accept is New channel from here. P3.15's eval is to be reworded to say so rather than expect a move offer. Chosen by the user on the status page on November 9, 2026, accepting the recommendation.
- `web_fetch` runs without a card only when the exact URL (scheme and host case normalized) appears in text the user wrote in this scope or in an earlier tool result of the same run; any URL the model composed itself waits for an approval card that shows the full URL, and a goal's standing permission can grant a host for unattended runs. A planted page could otherwise send conversation text to another server in a GET's path or query. Box P2.25 builds it. Chosen by the user on the status page on November 9, 2026, accepting the recommendation.
- A copy of the database before startup migrations: when migrations are pending, the server first writes a copy with SQLite's online backup to `backups/` in the data directory, named for the schema version and time, keeps the last three, logs where it went, and refuses to start if the copy fails; the README says how to roll back. An unattended image upgrade otherwise changes the only copy of the user's data in place. Box P2.21 builds it. Chosen by the user on the status page on November 8, 2026, accepting the recommendation.
- Offline use: not now. No service worker; the app says plainly when it can't reach the server. Everything it does needs the server, and a cached copy would go stale and bring cache bugs after each update. Revisit if reading channels away from the server turns out to matter. Chosen by the user on the status page on November 9, 2026, accepting the recommendation.
